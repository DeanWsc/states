# React and Next.js

The kit has no framework in it, and that is deliberate. Copy `kit/` into the
project and call the builders as plain functions from wherever you render.

## 1. File layout

```
components/
  iso -> states/
    kit/            color.mjs html.mjs css.mjs state.mjs tokens.mjs ui.mjs audit.mjs
    tokens.css      generated: tokensCss(palette()) + themesCss(...)
    components.css  generated: componentCss(palette())
```

Generate the two CSS files once and commit them, or generate them in a build step.
Either way they are ordinary CSS with no dependency on the kit at runtime.

## 2. The split

Keep geometry and markup in plain modules. Keep interactivity in client
components that receive element props, not markup strings.

```tsx
// components/queue.tsx — a server component, no "use client"
import { panel, field, button, toggle, empty } from "./states/kit/ui.mjs";

export function UploadQueue({ folder, error }) {
  return (
    <>
      {panel({
        title: "Upload queue",
        note: "Files are scanned before they leave your browser.",
        children: [
          field({ label: "Destination folder", name: "folder", value: folder, invalid: !!error, message: error }),
          `<div class="actions">${button({ label: "Choose folder" })}${button({ label: "Clear", variant: "quiet" })}</div>`,
        ].join("\n"),
      })}
      {empty({ title: "Nothing has failed yet" })}
    </>
  );
}
```

Those builders return HTML **strings**, which is the wrong shape for JSX. Two
ways out, both fine:

- Render the string with `<div dangerouslySetInnerHTML={{ __html: markup }} />`
  when the markup is fully generated by the kit and contains no user input.
- Wrap them as tiny components when you want JSX ergonomics:

```tsx
// components/states.tsx
import { button as buttonHtml } from "./states/kit/ui.mjs";

export function Btn(props: Parameters<typeof buttonHtml>[0]) {
  return <span dangerouslySetInnerHTML={{ __html: buttonHtml(props) }} />;
}
```

Neither is pretty. That is the honest cost of keeping the audit and the framework
apart: **the audit reads static HTML, so the markup has to exist as static
HTML.**

## 3. Server components

Everything above works in a server component, because nothing in it touches
`window`. The tokens are computed at build time by `palette()`, which is a pure
function.

That is the main reason to keep the kit framework-free: the whole design system
can be evaluated at build time, so a contrast failure is a build failure rather
than something a browser discovers at 3am.

## 5. The two traps

Each of these costs an afternoon the first time.

### The payload trap

A page that renders forty components through the generators produces forty copies
of the same markup, and React's reconciliation has nothing to compare. The
symptom is a page that feels sluggish on a mid-range phone while every individual
component looks fine.

**Fix:** render the static markup once on the server and hydrate only what moves.
`panel()`, `empty()` and `row()` output never changes, so nothing about them needs
to be a client component.

### The hydration mismatch

If the markup is built at render time from something that differs between the
server and the browser — a media query, `Date.now()`, a random id — React discards
the server HTML and re-renders, and you get a flash plus a warning.

**Fix:** ids come from `nextId()`, which counts in module scope. On the server that
counter differs from the browser's, so a component rendered on both sides will
mismatch. Either render those parts on the server only, or pass the ids in:

```tsx
// Generate ids once, pass them down, so both renders agree.
<Fields idPrefix="upload-queue" />
```

The `field()` builder takes an `id`, and `toggle()` and `checkbox()` accept one
through their label. Use it whenever a subtree can render on both sides.

## 6. Do not expose className

The tempting shape is a component that takes a `className` so it can be styled
from outside:

```tsx
// Do not do this.
export function Btn({ label, className = "" }) {
  return <span dangerouslySetInnerHTML={{ __html: buttonHtml({ label }).replace('class="btn"', `class="btn ${className}"`) }} />;
}
```

This breaks the skill silently. The audit matches CSS rules against class names, so
a caller who writes `className="btn btn--lg"` gets the default rules plus their
own, and a caller who writes `className="primary-button"` gets **no state rules at
all** — no hover, no focus, no disabled — and the audit will report every state
as missing with no obvious cause.

Let the component own its classes. If you need a variant, add it to the generator
so the states come with it:

```js
button({ label: "Save", variant: "danger" })
```
